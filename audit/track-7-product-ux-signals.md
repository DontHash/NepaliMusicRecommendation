## 2. What is already strong (with evidence)

- **Hybrid lyrics search that degrades gracefully.** Title/artist hits first, then dense+BM25 lyric hits (`web_app/server.py:186-199`); while the encoder warms, it serves lexical results with `warming:true` and auto-refreshes the same query (`app.js:516-533`, `server.py:190-199`); failure of the lyric backend still returns title hits (`server.py:155-157`, `tests/test_web_app.py:101-106`). This is better cold-start UX than most POCs.
- **Genuinely novel explainability engine.** Per-line joy/sadness/anger probabilities aggregated from window vectors (`music_rec/mood_attribution.py:245-276`), soft mode with three intensity tiers plus a calibrated hard mode (`app.js:212-231`, `PROJECT_GUIDE.md:761-768`), per-line hover tooltip with raw probabilities (`app.js:384-399`), and a polarity gauge (`app.js:353-363`).
- **Mood-aware browsing beyond the seed song.** Euclidean neighbors in mood space plus per-emotion top charts (`music_rec/mood_neighbors.py:72-92`, `server.py:222-243`) — a browsing surface no consumer music app exposes for mood profiles.
- **Nepali-language mood phrase + confidence from teacher labels** (`music_rec/mood_attribution.py:308-315`, `mood_phrases.csv:1-3`) shown in the hero label (`app.js:310,312-318`).
- **Ad-hoc paste analysis with transliteration metadata** and a stated script detection (`server.py:246-268`, `app.js:603-623`) — a credible "analyze my own lyric" loop.
- **Real diagnostics instead of silent failure**: search errors, zero-result notes, and warming notes all render (`app.js:562-580`), asserted by tests (`tests/test_web_app.py:146-156`).
- **Resource hygiene**: donut geometry/materials disposed on rebuild (`app.js:109-116`), DPR capped at 2 (`app.js:35`), ONNX query encoder + CPU inference to avoid GPU/WebGL contention (`PROJECT_GUIDE.md:805-823`).

## 4. Top 10 improvements (ranked by impact / effort)

1. **Anonymous signal instrumentation (S).** Add a fire-and-forget `POST /api/events` (batched, JSONL/SQLite) and emit from existing handlers: search issued + latency + path (`title/lyric/lexical/warming`), result impressions (position, `match`), result click, `song_open(source)`, neighbor/mood-chip click, mode toggle, paste analyze (metadata only). Client ID = random UUID in `localStorage`; **never log pasted text**; 30–90-day retention, disclose in UI (Nepal Individual Privacy Act 2018). First metrics: zero-result rate, CTR@k, result→open rate, neighbor CTR, session depth. Dependency for everything below.
2. **Surface matched lyric line + snippet in results (M).** Extend `_lyric_hits` (`server.py:147-174`) to return the best-matching lyric line and token spans (BM25 already scores the query against lyrics); render a 1–2 line clamped snippet with highlight in `app.js:553`, and a "why" tooltip on the `lyrics` badge. This makes the differentiated capability visible; gain: perceived precision/trust.
3. **Explicit feedback + label collection (S/M).** Thumbs up/down and "mood right/match mood" on neighbor rows, "not this mood" on the song hero; store with model/artifact version. Doubles as cheap label collection for the 147-song mood gold set and as a rejection signal for a future ranker (`algo`/`data` tracks consume it).
4. **Search layer upgrade (M).** `/api/suggest` prefix+typo suggestions over title/artist, recent searches in `localStorage`, filter chips using existing fields (`artist`, `category`; expose `script_style_original` from `corpus_final_v2.csv`), and a "did you mean" built from `TypoMap` (`music_rec/typo_map.py`, already shipped) applied to titles/artists. Implement as an ARIA combobox as part of the same change.
5. **Zero-result recovery (S).** On empty results, return relaxed alternatives: fuzzy title/artist candidates, artist-page suggestion, and a CTA to the three mood top charts. Compose the message from data, not a string literal (`app.js:567-569`).
6. **Deep links + share (S).** `?song=4024` (or hash) with `history.pushState` on load; render on boot; copy-link and browser back. Cheap, and it makes the analytics session model coherent.
7. **Accessibility baseline (M).** Labels + `aria-label` for search/paste; `role=combobox/listbox/option` with arrow-key/Enter handling for results; `aria-pressed` on legend/mood/mode chips; `role=status`/`aria-live=polite` for loading and errors; visible `:focus-visible`; 24×24 minimum targets; `prefers-reduced-motion` static mode; a text alternative for the donut (legend already provides text shares). Target WCAG 2.2 AA.
8. **Mobile + error polish (M).** Tap a lyric line → persistent info bar with the emotion breakdown (instead of hover-only tooltip); clear stale payload on failure and add retry; responsive header; `100dvh`; larger touch targets; WebGL feature-detect with graceful "2D mode" or message.
9. **"Mood radio" + listen handoff (M).** One button that builds a continuous queue over mood space (reuse Euclidean neighbors + MMR, `recommender.py:199`, `mood_neighbors.py:72-92`), plus a "Listen on YouTube/Spotify" outbound link per song. This converts a read-only analyzer into a lean-back loop without audio rights, and generates the skip/dwell events instrumentation needs.
10. **Perf/polish hardening (S/M).** Content-hash vendor filenames with `immutable` long cache (keep `no-cache` only for `index.html`/`app.js`); pause rendering when the tab is hidden; optional static/2D donut for low-end devices; loading skeletons; fix `innerHTML` injection with `textContent` (`app.js:436,553`).

## 5. Verdict

This area lacks **scale** in users and signals, but that is not the only problem: it also has **product-engineering gaps that more scale would not fix**. The recommendation engine and per-line mood explainability are genuinely differentiated and ahead of consumer apps at the feature level; the shell around them is a demo, not a product loop. There is no signal capture, no playback handoff, no URL state, no onboarding, no accounts/library, no accessibility, no mobile affordance for the core explanation, and only a hardcoded first song. The good news: the missing pieces are mostly S/M web work that plugs directly into existing artifacts (`mood_vectors.csv`, lexical index, mood_phrases), so with a handful of sprints the same engine can support a credible mood-first Nepali music product. Without item 1, however, nothing downstream — personalization, rankers, UX evaluation — can improve; that is the P0.

- Contrast failure for `.dimmed` and soft-tier colors is likely but not computed per blended color; I did not run a contrast checker.
- The true share of non-Nepali (Hindi/English) songs is unknown: no language labels exist; `PROJECT_GUIDE.md:834-836` states it qualitatively. `category` is script style, not language.
- Whether any deployment adds analytics/proxy logging outside the repo is unknown; nothing in-repo captures signals.
- XSS assessment is static: I did not attempt to inject artifacts through the corpus.
- `tests/test_web_app.py` skips when window artifacts are absent, so I could not confirm runtime behavior beyond the assertions I read.
