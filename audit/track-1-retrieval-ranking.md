## 2. What is already strong (with evidence)

- **The correct two-stage skeleton exists and is genuinely separated**: candidate generation (`_rank` top-`ann_top_k`, `recommender.py:137-180`) → duplicate collapse → MMR to final 10 (`recommender.py:193-199`). It maps cleanly onto the industry retrieve→rank→re-rank funnel; only the *ranking stage content* is POC-level.
- **Hybrid lexical+dense fusion is the right call for verbatim Nepali lyrics, and it is measured**: dense-only lyric nDCG@10 0.2575 (`eval_dense_control.json:12`) → hybrid 0.9223 (`eval_v2_report.json:11-18`); hard truncated 0.155 → 0.9565 (`eval_v2_hard_dense_control.json:4`, `eval_v2_hard_report.json:3-10`). That is a real, not cosmetic, gain.
- **Window max-similarity correctly fixes mean-pool dilution**: 48-token/24-stride windows with per-song max aggregation (`embeddings.py:204-245`, `window_search.py:34-42`).
- **Query normalization chain is thoughtful**: transliteration triggered on any Latin char (`query.py:45-50`) with English gate, lexicon/context tables (`lyrics_pipeline/transliterator.py:521,550`), matched to the same tokenizer on the lexical side.
- **The fusion gate is eval-motivated, documented, and protects mood search** (`lexical.py:191-216`, `PROJECT_GUIDE.md:334-338`), with hybrid-vs-dense controls per query type.
- **Duplicate collapse is exact-lyrics grouping (`dedup.py:31-48`) — O(total tokens) build, O(k) query — not the O(n²) heuristic the brief feared.** Near-dup rejection is deliberate and documented (`dedup.py:8-10`).
- **Eval harness is above typical POC rigor**: separate dense controls, hard non-verbatim set, mood weak-label + human gold layers (`eval/queries.py:167-202`, `eval/mood_retrieval_eval.py:1-16`), per-query JSON reports.
- **Exact artist queries work as a filter**: recall@50 0.9986 (`eval_v2_report.json:3-10`), though this mostly proves the hard filter, not ranking.

## 4. Top 10 improvements (ranked by impact/effort)

1. **Add a learned re-ranker over the existing top-50 candidates (M).** Emit a feature row per candidate — window max-sim, song cosine, BM25+phrase bonus, fuzzy/fusion scores, normalized query-token overlap, sentiment alignment, dedup group, artist/category match — and train LambdaMART/LightGBM with `eval/queries.py`-style weak labels first, then real clicks. Where: new `music_rec/rank.py`, called at `recommender.py:193-199`. Expected: replaces gaps 1/2/9; the single biggest quality lever. Depends on #2 for labels.
2. **Log impressions, clicks, skips, query text, position, and a session/anonymous user id (S).** Add middleware in `web_app/server.py` and a JSONL/Parquet sink. Expected: unlocks LTR, personalization, off-policy eval, and position-bias correction. Depends on nothing.
3. **Make window retrieval sublinear or two-stage (M).** Either ANN (HNSW/Voyager, IVF-PQ + refinement) over 62k windows with re-scoring of the top ~2k in full precision, or song-level ANN → window re-score only the top candidates. Where: `window_search.py:34-42`, `index.py:11-17`. Expected: removes the 27 ms today and the 19 GB/timestep wall at 100x (gap 3).
4. **Intent + entity routing and fielded retrieval (M).** Classify each query (artist / title / lyric / mood / mixed), link entities against artist/title catalogs with fuzzy matching, then build a fielded BM25 index (lyrics + title + artist) with boosts, and compose filters (artist+mood). Where: new `music_rec/understanding.py`; index in `lexical.py`. Expected: fixes gap 6 and multi-intent failures (Q8).
5. **Replace min-max + 0.65 with scale-free or calibrated fusion (S).** Try RRF, or logistic regression on the two score ranks/scores trained on eval + logged clicks; allow per-intent weights. Where: `lexical.py:288-296`, `config.py:61`. Expected: gap 2, robust as IDF and catalogue shift.
6. **Persist and serve the lexical/BM25 index; incremental updates (M).** Serialize the sparse matrix + auxiliary structures (or move to OpenSearch/Lucene when >50k songs) instead of rebuilding per process (`lexical.py:74-101`). Expected: gap 4; 6.7 s → load-time mapping; enables multi-worker.
7. **Metadata and popularity enrichment (M).** Acquire release year, plays/popularity, genre, language; store alongside corpus. Expected: gaps 9/16; enables freshness/popularity in re-rank and LTR features.
8. **Mood intent → probe-conditioned ranking (M).** Add a mood query classifier mapping keywords to target sentiment/mood vector; pass `target_sentiment` from `recommend_by_text` (`recommender.py:233-239`) and blend probe probabilities into reranking (beyond `sentiment_weight=0.15`). Expected: gap 10; mood precision above the 0.709 plateau.
9. **Query relaxation and synonym/typo coverage (S–M).** Drop-rare-term fallback when recall is empty, per-token fuzzy artist matching, mood synonym lexicon, and Hindi roman lexicon extension. Where: `query.py`, `recommender.py:223-231`, `typo_map.py`. Expected: gaps 6/17 failure modes; cheap wins on long-tail queries.
10. **Upgrade evaluation to product-grade (M).** Multi-relevant human gold for a few hundred queries, head/tail and per-language slices, bootstrap CIs, and an offline replay harness for re-ranker A/B. Where: `eval/`. Expected: gaps 8/15; makes every other change measurable and prevents regressions hidden by single-gold nDCG.

## 5. Verdict

**For ranking quality, this system lacks scale. For serving, it also lacks scalability.** The architecture is the right shape — separate retrieval, fusion, dedup, re-rank; calibrated evaluation; transliteration glue — and at 4,157 songs the exact paths are fast (27 ms window scan, 6.7 s index build). But the claim "only lacks scale" is not yet true: the hot path is an exact 62k-window numpy scan with no ANN, BM25 and its 548k-posting fuzzy n-gram index are rebuilt in memory per process, metadata filtering is O(N) pandas per query, and there is no learning, personalization, feedback loop, or cache anywhere. Adding users and songs without first fixing #1–#7 would multiply a heuristic, not make a recommender.

## 6. Open questions / uncertainty

- **Mode divergence**: evals run with window search on (`run_eval.py:35` default config), while the web app explicitly sets `use_window_search=False` (`web_app/server.py:113`), so user-facing behavior differs from the published numbers; I could not verify the web app's end-to-end rankings.
- **No end-to-end latency measured**: I timed the numpy/BM25 stages only, not ONNX/torch encode or transliterator load (avoided model downloads).
- **Artist metric is near-trivial**: recall@50 0.9986 mostly reflects the hard artist filter (`recommender.py:150-163`); within-artist ordering has no ground truth.
- **Eval circularity**: lyric gold is constructed from the corpus line itself (`queries.py:79-91`), so 0.92 nDCG is a retrieval-feasibility score, not a relevance judgment.
- **Seed proxy is harsh**: same-artist gold penalizes a content recommender by design; 0.156 is not "radio quality" but it is also not validated as a fair proxy.
- **Sentiment probe provenance** (`mood_probe.npz`, 4157 songs) and mood weak labels (Gemini) were not re-validated here; mood conclusions inherit their error.
- **Brief correction**: `dedup.py` is not O(n²); the real O(N) risks are metadata scans (`recommender.py:132`) and in-memory index builds.
